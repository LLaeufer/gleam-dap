# What does CI run?

**Already built:** `.github/workflows/ci.yml` runs on pushes to `main` and
on pull requests:

- a test job on OTP 27 and OTP 28 with Gleam 1.19.0: `gleam format --check
  src test packages`, `gleam test`, packaging the adapter, and `gleam test`
  again with `GLEAM_DAP_COMMAND` pointing at the packaged adapter;
- a job that builds the VS Code extension on OTP 27 and uploads the
  `.vsix` as an artifact.

## Where and when it came up

PLAN.md's testing section: "A CI workflow running both on a recent OTP
version." It came up at the end of step 4.

## What I chose

The two jobs above, with the adapter log uploaded when a test job fails.

## Options

### OTP versions: 27 and 28 (chosen) vs. only the latest

- The plan requires OTP 27 or newer, and step 1 asks for the spike to work on
  27 and 28. Testing both catches `int` differences between releases.
- Doubles the CI time (a few minutes each).

### Gleam version: pinned 1.19.0 (chosen) vs. latest

- Pinned keeps CI reproducible; the golden file of breakable lines would
  otherwise fail whenever a new compiler moves them, on unrelated PRs.
- A newer Gleam that changes code generation won't be noticed until the pin
  is bumped. Bumping it is a one-line change, and the golden test then
  shows exactly what moved.

### Testing the packaged adapter too (chosen) vs. only the source build

- The package rewrites every dependency module (see
  [09-packaging.md](09-packaging.md)); running the end-to-end tests against
  it is the only way to catch a broken rename.
- Runs the slow end-to-end tests twice.

### Format check scope: `src test packages` (chosen) vs. everything

- The fixtures are deliberately not formatted: the tests set breakpoints
  by line number, and `fixtures/sample/src/sample/flow.gleam` has a
  multi-line expression on purpose to test stepping over it.

## Why

This tests what users actually run (the package and the extension) on every
supported OTP version.

## How to change it

Edit the matrix and the `gleam-version` in `.github/workflows/ci.yml`.
Whether the workflow passes on GitHub hasn't been seen yet: it was written in
a sandbox without access to GitHub Actions.
